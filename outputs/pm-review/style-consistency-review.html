智能推荐机制说明
与「五禽戏 / 太极 / 八段锦 × 虚拟形象」一致性核查

本报告回答两个问题：① 软件当前依据什么给用户推荐功法与音乐；② 三大功法在应用里的动作与虚拟形象演示的动作，在名称、顺序、幅度、时长、节奏五个维度上是否一一对应。全部结论均来自源码与实机探针，附证据行。

00结论速览

推荐机制的一句话事实

软件不是读设备体征来推荐的。它读的是用户自己回答的 7 道问诊题（主壳）与节气 + 上次选的音调/拳种（s4）。设备体征（心率 / 睡眠）在主壳里已被如实标注为「未接入」——这一点做得是对的，没有拿假数据糊弄。

动作一致性的一句话事实

只有八段锦是「真对应」的：8 式名称、顺序与教练小窗里那个房间版小人逐条对齐。五禽戏与太极在整个产品里没有任何可动的虚拟形象——实机进去，教练小窗是一个空占位框，写着「该式暂无示范动画……图片也未找到」。

01软件如何推荐功法与音乐

产品里存在两套并行、互不读取的推荐链路。它们各自成立，但结果可能互相打架——这是下面要指出的第一个结构性问题。

链路 A · 主壳问诊推荐（7 题 → 四项决策）

⚠️ 主壳的「帮我选」按钮不读问诊答案

首页「帮我选」按下后执行的是 state.rec = Math.floor(Math.random() * 3)——纯随机换一个音调，与用户的身体状态、与刚才答的 7 道题没有任何关系。这个按钮的文案（「智能推荐练习」）与它的行为不匹配。

链路 B · s4 首页「今日推荐」（节气 + 记忆偏好）

s4 子应用首页另有一个推荐卡，来源完全不同（train/src/views/HomeView.vue）：

  • 节气：currentTerm()（Meeus 太阳视黄经算法）→ 决定首页引言与「主××」标签
  • 音调：localStorage['xianyang.tone'] → 取 TONE_HOME 里的 what / why / 体验标签
  • 拳种：localStorage['xianyang.style']
  • 用时：Σ moves[].sec + 30s → 八段锦 7×90+60+30 = 690s ≈ 「约 12 分钟」

⚠️ s4 的「帮我选」也是假的

代码写的是 const sid = selectedStyle === 'auto' ? 'baduanjin' : selectedStyle。也就是说选中「帮我选」后，推荐卡永远显示「八段锦」——不读问诊答案、不读节气、不读任何状态，只是一个内容固定的占位。

⚠️ 两条链路互不相通

主壳问诊算出的「羽调 + 招牌 3 式」不会传到 s4 首页；s4 首页选的音调也不会回写问诊结论。用户在主壳被推荐一套、进 s4 看到另一套，是当前设计的常态。此外，主壳进入 s4 的固定入口把参数写死为 style=baduanjin&tone=gong，所以问诊算出的「羽调」在真跟练页里并不会生效。

2.2 幅度：房间版小人的肘部在数学上永远伸不直

这不是渲染 bug，而是动作库手位设计带来的先天约束。对 721 帧逐帧解算左右肘内夹角：

指标左臂右臂含义

根因

小人的臂长被设为 上臂 43.7 + 前臂 38.3 = 82（与姿势数据同尺度）。而动作库规定「手到肩」的距离上限约 76.6，中性「抱球」手位只有约 51。手离肩的距离 ＜ 臂长 ⇒ 肘必然有折角，数学上无解。上臂被迫外弓成「∏」形。

对跟练体验的影响

八段锦第 1、2 式（托天、开弓）的卖点就是「把手臂拉到最长、拔伸肩背」。而主壳动作要点里写的是「两臂伸直，肩沉肘坠」。用户看到的示范却是弯着胳膊——示范幅度小于文字要领。对「照着学架子」的新手，这是直接的动作误导。

03差异点清单：具体位置、影响与建议

D1五禽戏的「存在性」在主壳与 s4 之间自相矛盾口径冲突

现象同一个功法，两个界面给出相反的说法。

  • 主壳（dist/app.js 首页「五禽戏」按钮）：弹层写明「素材未随包交付——五禽戏（虎鹿熊猿鸟）目前没有动作示范素材与判定标定，所以没有开放练习入口」。这是诚实且正确的做法
  • s4（train/src/data/styles.js）：status: 'ready'、badge: '已上线'，5 式带完整 tip / cue / 照片路径；首页还给它一个可点的胶囊按钮。

实测在 s4 首页选「五禽戏」后：走「启动摄像头并起式」不会进入五禽戏（准备页把功法硬编码为八段锦）；但走「查看预录演示」会把 wuqinxi 带进跟练页，此时教练小窗显示一个空占位框。

附带缺陷这行降级文案有 40 余字，而教练小窗只有 96×108。实拍可见文字溢出并糊成一片字块（见对照截图 coachwin-wuqinxi.png），反而比没有提示更让人困惑。

建议二选一，不要并存：(a) 把 s4 的五禽戏胶囊改为禁用态（灰显 + 角标「开发中」），与主壳口径统一；(b) 或把主壳弹层文案改为「练习素材开发中，当前仅八段锦可练」，两处都指向同一句。另需把 /photos/*.jpg 决定是补上还是删掉路径——留着 404 的引用比没有更糟。

D2太极在所有界面里都不可见，只能靠手输 URL 进入幽灵功能

现象主壳功法切换段只有三个按钮：八段锦 / 五禽戏 / 帮我选——没有太极（全文检索「太极」在主壳 dist/app.js 里零命中）。s4 首页胶囊也只有八段锦与五禽戏两个。太极只存在于 styles.js 里，且只有 1 式（起势）。

实测?style=taiji 可达（resolveStyle 放行 partial 状态），进页后同样是空占位：

【style=taiji】 当前式名 .cb-name : 第 1 式 · 起势 教练小窗【可见】SVG 小人: false 降级占位【可见】.ph.miss : true 照片请求 : ["404 /photos/tj01.jpg"]

影响对普通用户影响为零（碰不到）；但它是评审/演示时的隐患——一旦有人深链进来看，会看到一个只有 1 式、且没有动画的残缺页面。同时它会给维护者「太极已经开始了」的错觉。

建议要么把太极正式纳入胶囊并明确标注「仅起势可用」，要么在 styles.js 里把 status 改成 pending（resolveStyle 会自动拒绝），让它在代码层面也真的不可达。推荐后者——口径与行为一致，成本一行。

D3虚拟形象与功法解耦：五禽戏时，被隐藏的小人其实在演八段锦沉默缺陷

现象教练小窗的形象索引 roomFigureIdx 只由式序决定，与功法无关：

TrainView.vue:468 const roomFigureIdx = computed(() => roomIndexForAppStep(stepIdx.value)) // 恒指向 roomMoves.js 那张【八段锦】10 式表

为什么现在没暴露因为动画键是 ${style.id}-${step+1}，即 wuqinxi-1；而 DEMO_ANIMS 里只有 baduanjin-1..8，查不到 ⇒ state = 'missing' ⇒ v-show 把小人藏了。「无动画」这个闸门恰好掩盖了「动画是错的」这个问题。

影响目前无可见影响。但这是一个沉默的耦合陷阱：任何人只要往 DEMO_ANIMS 里补一条 wuqinxi-1（而这看起来是"顺手就做了"的事），小人会立刻开始用托天的动作去演示虎举——没有任何报错、没有任何警告，只有视觉上的错。

D4同一式存在两份时长数据，实际播放按其中一份，偏差最大 40%数据冗余

现象demoAnim.js 与 roomMoves.js 各写了一份每式时长，前者决定播放、后者无人引用。详见 §2.3 对照表：播放/自述比值在 0.70× 到 1.40× 之间，合计 46.8s vs 54.0s。

影响「摇头摆尾」「两手攀足」被加速约 30%，对腰背不适人群偏快；第 8 式被放慢 40%（这个方向是对的）。

建议让时长只有一个权威来源。最小改动：在 DemoAnimation 里，当版式为 coach 时把 dur 取 ROOM_MOVES[idx].dur（顺便把这份死元数据接活）；或者反过来删掉 roomMoves.js 的 dur 字段，只留 demoAnim 一份，并把比值差异当作有意的时间轴压缩记录下来。

D5单遍播放模式下，7 式的收势段被截掉 19%~35%时序缺陷

现象定格点取「最后一个 phase:'end' 关键帧」，8 式里有 7 式的定格点落在 u ≈ 0.65~0.81，收势/归位段没播完就定格了（详见 §2.4）。

影响仅在计时闸门（?coachGate=time）与降级路径下出现。用户看到小人停在"手臂下落途中"，而卡片已写「示范完毕·请跟我做」——文案与画面不同步。默认判定闸门因为持续循环，不受影响。

建议把归位段也标成 phase:'end'（语义上也确实属于结束段），或把 onceEndT 改为 Math.max(最后一个 end 帧, dur)。一行改动，且不触碰任何版式。

D6示范幅度小于文字要领：肘部数学上伸不直（64.6% 的帧 <110°）内容约束

现象房间版小人 721 帧逐帧解算：肘内角中位 93.9°、极限 133.5°、64.6% 的帧小于 110°。

归因臂长 82（43.7+38.3），而动作库手位到肩的距离上限约 76.6、中性抱球位仅约 51。手离肩比臂长短 ⇒ 肘必然弯。这是动作库手位设计的先天属性，不是渲染 bug——房间版原页也是同样的表现。

影响托天、开弓这类以「拔伸」为卖点的式子，示范是弯着胳膊的；而主壳动作要点写的是「两臂伸直，肩沉肘坠」。用户照着学架子会被误导。

建议三条路，按代价排序：(a) 标注优先——在动作要点里把「两臂伸直」改成「手臂尽量向上伸展，不必强求绷直」，让文字与示范一致，零风险；(b) 对齐绘制——把绘制侧肩点与解算肩点对齐、并收掉腕部发光圆环，视觉上"看起来更直"，改动小；(c) 治本——改动作库让手位离肩更远（R_MAX 与各式中性手位），需要重建产物 + 逐像素回归，属第三批，须先确认。

D7首页承诺「约 12 分钟」，跟练页没有时间预算承诺落差

现象moves.json 的 sec（7×90 + 60 = 690s）只在 s4 首页用来估算时长；跟练页完全不读，节奏由判定闸门驱动——没通关永远停在这一式，没有倒计时放行。

影响同一套八段锦，用户可能 3 分钟走完、也可能 30 分钟卡在第 1 式。首页的「约 12 分钟」因此无法兑现。

建议不改逻辑，只补文案：准备页「约 12 分钟」后加一句「实际时长随掌握程度变化，做到位即进下一式」。或把「约 12 分钟」改成「8 式 · 一次一遍」这类不含时间承诺的表述。

D8主壳的练习屏是静态复刻页，百分比是写死的易混淆

现象dist/app.js 的 pgPractice() 里，上半身 92% / 下半身 88% / 取景 22% 全是硬编码字符串，与任何识别结果无关。

影响通过 ?screen=practice 直达能看到这组"假"数据。它本身就是一张 1:1 复刻的设计稿页，但如果用户（或评审）误以为这是真跟练，会立刻发现「数字不动」。真正的跟练在 s4。

建议这条与本轮第一、二批已完成的改动相关：s4 跟练页顶栏已接真实可见度（无人时显示「—」、条宽 0%）。剩下的只是主壳这一屏要不要加一句「效果预览」标注——归入第三批待确认项，本轮不动。

04建议汇总（按风险与代价排序）

下面每一项都标注了改动范围。P0 全部是文案与开关级别，不触碰任何已冻结版式；P1 是一致性修复，改动集中在 train/ 内的数据与映射；P2 需要内容侧输入，触发产物重建。

P0-2

P0-3

主壳是随机换音调，s4 是固定回落到八段锦。若不打算接逻辑，至少把副文案从「智能推荐练习」改掉，避免承诺过度。

动作要点里「两臂伸直」→「尽量向上伸展，不必强求绷直」；准备页「约 12 分钟」后加一句「做到位即进下一式」。纯文案，零风险。

P1-1

roomFigureIdxFor(styleId, stepIdx)，非八段锦返回 null。这是本次核查发现的最高价值修复——把一颗埋在未来的雷拆掉。

让 coach 版式的 dur 取 ROOM_MOVES[idx].dur，或删掉重复字段。同时复核第 5、6 式的节奏是否偏快。

P1-3

归位段补 phase:'end'，或 onceEndT 兜底到整段末尾。

P2-1

需要 PM 输出「式名 + 要领 + 可见性需求 + 关键帧」。在此之前，维持现状的「如实标注、不做假按钮」就是正确做法——主壳这一处做得很好，应当保持。

P2-2
