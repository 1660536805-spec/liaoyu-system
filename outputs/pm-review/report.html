产品评审与改善建议 · 以产品经理视角审「整体应用」
评审日期：2026-10-10 评审对象：主壳 dist/ + 跟练子应用 dist/s4/ 方法：读源码 + 真机走查 + 运行时探针 本轮不改任何前端代码

一句话结论

界面完成度很高，但「看起来是真的」和「真的是真的」之间还有一段距离。 产品有一个非常亮眼的品质：109 个可点元素 0 个死按钮，没接的能力还会自动标成「暂未接入」并如实告知—— 这个诚实度超过了绝大多数参赛作品。

真正的问题不在"缺功能"，而在三处"假的比真的还显眼"：首页节气日期是写死的、跟练页最显眼的三个百分比是常量、 问诊 7 题问完就丢。这三件事都会在评委/用户追问一句之后崩塌，而且修复成本都极低。

如果本轮只做三件事：

  1. 把首页「今日 · 霜降 / 10月23日」换成真实节气与日期 （低风险、当天可完成）
  2. 把跟练页顶栏那三个百分比绑到真实可见度，未检测到人体就显示「—」（低风险、半天）
  3. 让问诊 7 题的答案真正影响推荐（曲目 / 式数 / 强度），或干脆收敛成 3 题偏好设置 （中成本）

二

P0 · 信任与正确性（建议本轮就修）

P0-1首页的「今日节气」是写死的

现象
首页黄金位显示「今日 · 霜降」，副行「10月23日 农历九月初三」。评审当天是 2026-10-10，节气早已不是霜降，日期也完全对不上。
证据
dist/app.js:343–344；同一串内容还出现在 :361（首页引用条「霜降水返壑…」）、:668（结束页食养理由）、:335（推荐理由文案）——共 4 处。
影响
这是首页第一眼看到的字。养生类产品最忌"连今天是什么日子都不知道"，一旦被指出，后面所有"顺时而食、节气调养"的说法都会被连带怀疑。
建议
接一个纯本地的节气计算（24 节气日期表 + 当前年份即可，无需任何接口）：节气名、公历日期、农历日期、节气释义、引用诗句、食养推荐全部随节气切换。四段文案做成一张 SOLAR_TERMS 表。
成本 / 风险
低（一个函数 + 4 处引用）/ 低（纯文本替换，不动版式；改动后按既有流程做逐像素回归，未触碰的屏必须 0 差异）。

P0-2跟练页最显眼的三个百分比是假常量

现象
真跟练页顶栏「上半身 92% / 下半身 88% / 取景完整度 92%」永远是这三个数，跟画面里有没有人毫无关系（假摄像头下"未检测到人体"时依然是 92/88/92）。
证据
train/src/views/TrainView.vue:40–54 是静态标记，数值与进度条宽度都写死。
但真实数据是有的
同一个文件里 updateDiag()（:528–558）用 MediaPipe 关键点真实算出上半身 / 下半身可见度与肩宽占比，结果写进 vis.text（:97 的 .diag 诊断条），并驱动底部文字提示；真实成绩还有一个「完成度 liveScore%」（:201, 238）。也就是说：真数据算出来了，只是没接到最显眼的那张卡上。
影响
动作识别是这产品的核心承诺。把常量放在最显眼处、把真实值藏在诊断条里，等于主动制造一个"一眼假"的把柄。反过来，把真值接上去，评委现场就能看到数字随人动而变——这是最划算的一次改动。
建议
三个数改绑 vis 实时值；未检测到人体时显示「—」而不是 92%；取景完整度保留红/绿告警配色，并让它的颜色驱动条件与 updateDiag 的判定保持一致。
成本 / 风险
极低（3 个插值）/ 低。

P0-3主壳「练习」屏与真跟练页的数字一模一样，容易被当成识别结果

现象
主壳那张练习屏（名画 + 人物图 + 绿色骨架 + 92%/88%/取景 22%）看起来就是"识别中"的界面，但它不启动摄像头、不做任何识别，骨架是写死的折线坐标。
证据
app.js:451–453（固定骨架点）、:462–464（92/88/22）；:806–807 进入这一屏时的 toast 原文：「示例演示：设计稿静态复刻页，未启动摄像头；真练请点「开始动作预览」」。
影响
用户在主壳练完一整轮（点"下一个"到第 8 式）后会进结束页看到 89 分，全程没有任何真实测量。这条路径是最容易让人误以为"AI 在看我"的路径，也是投诉风险最高的一条。更麻烦的是：这张屏里唯一的真练入口藏在左侧 tab「动作示范」里，而主按钮是"下一个"。
建议
给它一个明确的定位——「动作图解 / 要领」页，而不是"识别页"：
  • 去掉三个百分比（换成"第 N 式 · 对应第 N 弦 · 要领摘要"这类真实信息）；
  • 骨架若保留，改为"示意骨架"并加注说明，或与人物图对齐（现在骨架浮在画面正中、人物在右侧，明显错位）；
  • 把「动作示范」提升为主按钮（"去真跟练"），与首页动线里的「开始动作预览」统一成同一个词。
成本 / 风险
中（改文案与版式，需逐像素回归）/ 中——涉及已冻结的设计稿版式，建议先给你看改动前后的对照图再决定。
三

P1 · 数据闭环与激励（下一轮）

P1-1问诊问了 7 题，一题都没用上

现象
7 步问诊完整可用（含上一步 / 跳过 / 未选拦截），答案存进 state.answers……然后就结束了。
追查补记
后补实地走查发现更严重的一层：这 7 步其实是同一道题重复了 7 次——题干固定为「你最近哪里容易不舒服？」，4 个选项固定为「颈肩 / 腰背 / 睡眠 / 情绪」，进度只是 第 N 步 / 7 在变。用户答到第 3 遍就会发现"这题我刚答过"，是比"问了不用"更直接的信任损伤。本轮 P1-1 已顺带换成 7 道递进题（部位 → 睡眠 → 情绪 → 精力 → 可投入时长 → 身体限制 → 最想改善）。
证据
全文件搜索 answers 只有 5 处：定义、重置、选择、上一步回填、下一步校验（app.js:8,757,759,760,761）。没有任何一处读取它来影响首页推荐、曲目或练习参数。
影响
"问了不用"比"不问"更伤体验——用户认真做完 7 题，回到首页发现推荐纹丝不动。这也让首页那个「为什么推荐给你」的说明变成了没法自圆其说的话术。
建议
二选一，别停在中间：
  • (A) 真用起来：答案 → 推荐映射（五音入五脏的脏象 → 首选曲目；肩颈/腰背 → 首选式序；睡眠 → 练习时段建议），首页推荐卡直接展示"因为你说了 X，所以推荐 Y"；同时把答案存进 localStorage，让「我的」能回看。
  • (B) 收缩：把 7 题砍到 3 题（最想改善 / 每天可投入时长 / 身体限制），定位成"快速偏好设置"，问完立刻落在首页推荐上。
成本 / 风险
中（(B) 更低）/ 低。

P1-2激励曲线 4 次打卡就顶到头

现象
模拟 5 次真实打卡后：「我的」显示 600 / 600（已满格）、阶段进度 7 / 8 节、已练 5 天。也就是说连续练 4 天就把经验条练满了。
证据
app.js:191 DESIGN{xp:360, xpMax:600, stageDone:3}；:529 xp = 360 + 打卡次数×60 ⇒ 第 4 次即 600；:532/:670 阶段进度 = 打卡天数 + 2 ⇒ 第 5 天 7/8。
影响
留存机制的生命周期只有 3–5 天，之后就无目标可追。对"日日精进"的产品定位是直接矛盾。
建议
改成以真实投入量推进：经验 = 累计练习分钟数 + 累计完成式数（加权）；阶段按"每节需要 N 次有效练习（含完成度门槛）"解锁；把「已练 N 天」与「连续 N 天」在文案上彻底分开（现在两个数在真实数据下会撞在一起）。
成本 / 风险
中（一处公式 + 文案）/ 低。

P1-3结束页把"假成绩"写进了真实记录

现象
结束页的分数、时长、命中数是假的（有免责说明，做得对），但点「完成打卡」时写入的是主壳这次静态浏览的式数与停留秒数——于是「我的」里就出现了一条"看起来练过、其实没练"的记录。
证据
app.js:499–504（假成绩）、:833–836（checkin(式数, 真实秒数) 写入 localStorage）。
建议
两条路都行，选一条：
  • 打通：把 s4 真跟练的结果（完成度、实际完成的式数、时长）通过 URL 参数或 localStorage 回写给主壳，结束页显示的就是真结果；
  • 分开：主壳结束页明确标成"示意页"，且不提供打卡按钮，打卡只在真跟练结束后发生。
现在这种"标注了是假的、但仍然允许记进真实档案"的中间态最危险。
成本 / 风险
中 / 低。
四

P2 · 工程与一致性（持续还债）

P2-1一个产品两套前端、两套视觉语言

现状
主壳是 无源码工程（直接手改 dist/app.js 884 行 + app.css 624 行，9 张设计稿 1:1 复刻）；s4 是完整的 Vue3 + Vite 工程，但对外只放行 /train 一个页面（其余 17 个视图会被弹回主壳）。
视觉断层
主壳：宣纸米 #FBF3E3 / 赭石 #B0552E / 青瓷玉 #6E8F7C。s4：theme-color #16130f（近黑）+ 荧光绿摄像头画面 + 深色小人。两侧并排时不像同一个产品。
影响
① 主壳每次改动都要做逐像素回归，"能改"的成本极高，产品迭代速度被锁死；② 两套 UI 各有一套「首页 / 音疗 / 我的」，数据不互通；③ s4 里 17 个不可达视图仍在源码与产物里，构建、克隆、CI 全都在为它们付费（仓库 165MB，最大单文件 21.6MB wasm）。
建议
分三步，别一次动大手术：
  • 短期（本周可做）：给主壳补一个最小构建层——把 app.js 拆成模块 + 一个 esbuild 打包脚本，产物保持字节等价。这样后续改动不必再手改压缩产物。
  • 中期：给 s4 做一次与主壳一致的配色映射（摄像头区域的荧光绿 → 青瓷玉系；深色房间 → 暮色宣纸），先把"同一产品"的观感立起来。
  • 明确边界：要么把主壳逐步迁进 s4 技术栈合二为一，要么正式宣布"主壳 = 品牌外壳（冻结），所有新功能只进 s4"，并把 s4 的 17 个死视图从产物里剔除以缩小体积。
成本 / 风险
中高 / 中（涉及架构，建议单独排期）。

P2-2没有账号，所有"长期数据"随时会清零

现象
打卡记录、身体数据、头像、音频偏好全部只存在本机 localStorage；界面已如实说明「本机演示版没有线上账号，换设备不会同步」。
影响
"连续打卡 7 天""累计 58 分钟"这类最有说服力的数据，清一次浏览器缓存就没了；换手机、换浏览器都归零。作为参赛作品可以接受，作为产品不能。
建议
低成本版：加「导出 / 导入我的数据（JSON）」两个按钮，至少让数据可迁移；正式版：接轻量账号（手机号 / 微信登录 + 云同步打卡记录）。
成本 / 风险
导出导入 低；账号体系 中高。

P2-3细节清单（低成本、可批量处理）

  • 主壳练习屏骨架与人物图明显错位（骨架在画面中央，人物在右侧）——见截图。
  • 跟练页「取景完整度」的告警配色与真实判定条件不一致：92% 也是红色进度条，颜色失去了信息量。
  • 桌面端并排布局下，教练画面里的文字（如「循环陪练中…」）有裁切；「当前式名」标签与卡片边缘叠在一起。
  • 启动台里 s4 的链接是 ?stage=1，而主壳生成的参数是 stage=point|line|arc——两处参数口径不一致，建议统一。
  • s4 的 18 个视图中，与主壳重复的「首页 / 音疗 / 我的」共三处，且 s4 的「我的」还有一处写死的 92 分（MeView.vue:75），建议随 P2-1 一并处理。
